◟◞ Radio Tower — Architecture Map

Every layer between an MP3 on a USB stick and a stranger's phone playing it on the same second as yours. · 18 Aug 2026
The one idea everything rests on. The programme is a pure function of wall-clock time. There is no playlist object, no "current track" variable, no per-listener position, no websocket. Station.at(now) takes an instant and computes which track is on air and how far into it — deterministically, from the library plus a fixed STATION_EPOCH.

Two consequences worth understanding, because they explain most of the design below: restarting the server does not interrupt the broadcast (the function doesn't care that the process died), and sync is free (two machines computing the same function of the same clock agree, with nothing passing between them). That is how a 512MB single-board computer serves a synchronised station without coordination machinery.

2The library — turning files into factsserver/lib/library.js
music/ → MUSIC_DIR
Your MP3s. Walked recursively, read-only, never modified. USB stick or SD card.
metadata extraction
music-metadata reads title, artist, duration, cover art. Duration is the load-bearing field — it's what the clock arithmetic runs on.
.cache/library.json
So a restart doesn't re-read every file over USB 2.0. Keyed on path + mtime + size.
auto-rescan · every 30 min
Roadmap #5. Adding one file changes the cycle length, which moves where "now" lands — by hours, growing with uptime. Everyone listening hears the music cut mid-bar.
↑ a sorted list of {path, title, artist, duration}
3The station clock — the sacred layerserver/lib/schedule.js
STATION_EPOCH
A fixed instant. Everything is measured from here. Change it on a live station and you re-deal the entire programme forever.
cycleSeconds
Sum of every track's duration. The programme loops with this period.
Station.at(now) → {track, offset}
elapsed = now − epoch → position = elapsed % cycleSeconds → walk the list. No state is read or written. This is the whole engine.
.upcoming() / .history()
Same function, different instants. Future and past are equally computable — which is why a programme guide is nearly free.
The hard rule. This file must stay a pure function of wall-clock time. If a feature seems to need stored playback state, it is the wrong feature. That constraint is what makes everything above and below it simple.

4HTTP surfaceserver/index.js · routes/api.js · lib/stream.js
EndpointWhat it does
GET /api/stationWhat's on air, the offset into it, the next 5, server time. The one endpoint that matters.
GET /api/healthTrack count, cycle length, memory, warm-up state.
GET /track/:id/streamThe audio. HTTP range requests — the browser asks for bytes N…M, so a listener joining mid-track fetches only from where they join. No transcoding, ever; the Pi couldn't.
GET /track/:id/artCover art. Re-parses the file per request — flagged as a probable problem on real hardware.
POST /api/rescanForce a library re-read. Unauthenticated — roadmap #6.
GET /api/scheduleNot built. The programme guide you asked for. Pure arithmetic over layer 3.
Static files are served straight from public/. There is no build step, no bundler, no framework — nothing to compile, nothing to break between writing a line and it running on the Pi.
↑ JSON + audio bytes over the network
5The player — where sync actually happenspublic/app.js · index.html · styles.css
clock-skew correction
Compares the server's clock to the device's and keeps the delta. A phone that's 40s off still lands on the right second.
join at offset
On tune-in: fetch /api/station, set audio.currentTime = offset, play. This one line is the sync.
drift correction
Re-checks periodically. Small drift → nudge playback rate. Large → hard reseek.
rollover
Loads the next track before the current one ends and switches at the boundary.
navigator.mediaSession
Not built — roadmap #3. Without it a locked phone shows no track name and no controls, and on iOS may stop entirely.
programme guide page
Not built — roadmap #0b. A timeline of what plays when, in the listener's own timezone.
The largest unproven surface in the project. Nothing has ever tested a real phone. iOS Safari needs a user gesture before audio starts, is historically fussy about setting currentTime — which this player does on every join — and suspends audio when a tab backgrounds. Emulated Chromium in the test suite does not settle any of that.

What happens when someone opens the URL

  listener taps "Tune in"
        │
        ├─→ GET /api/station ────────────────→ Station.at(Date.now())
        │                                            │
        │                                     library (cached) + STATION_EPOCH
        │                                            │
        │   ← { track, offsetSeconds: 87.4, serverTime, upNext[] }
        │
        ├─→ correct for this device's clock skew
        ├─→ audio.src = /track/abc123/stream
        ├─→ audio.currentTime = 87.4      ← the sync, in one line
        └─→ play()
              │
              └─→ GET /track/abc123/stream   Range: bytes=1400000-
                        └─→ fs.createReadStream(path, {start})   no transcode

  every few seconds:  re-check offset → drift < 0.5s ? nudge rate : reseek
  at track end:       roll over to upNext[0]

  ── nothing above was coordinated with any other listener ──
  ── they all computed the same answer from the same clock ──
