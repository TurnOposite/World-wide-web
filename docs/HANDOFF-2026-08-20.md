## 2. The one real bug found, and the easiest hot-fix path

**Browser cache serves stale JS after every deploy.** Diagnosed from inside the
live page: `fetch('/viz.js',{cache:'no-store'})` returned the new file while
`await import('/viz.js')` returned the old module (2 presets vs 3). `#vizStage`
was in the served CSS but in no entry of `document.styleSheets`. Ctrl+Shift+R
fixed everything instantly.

Consequence: the last two deploys both landed correctly and both looked like
silent failures. Worse, every listener who has ever opened the station is pinned
to whatever JS they first cached, with no signal and no fix you can ask a
stranger to perform.

**Easiest hot-fix path, in order of effort:**

1. **Right now, no code:** Ctrl+Shift+R. Only fixes the person who presses it.
2. **One-line server fix (do this):** `Cache-Control: no-cache` on the HTML entry
   point and on `.js` in `server/index.js`'s `express.static` options — leaving
   `/assets/backdrops/*.webp` cacheable, since those are genuinely immutable.
   `no-cache` still allows a 304, so it costs a revalidation round trip, not a
   re-download. Check the current headers with `curl -I` first; don't assume what
   `express.static` is sending.
3. **Belt and braces:** content-hashed query strings on the imports. More work,
   no bundler needed, but only worth it if step 2 proves insufficient.

Full evidence is already written up inside
`PROMPT-cache-and-stage-defaults.md` — run that and Job 1 is this fix.

## 3. It did not do what Ortis asked for. Being straight about that.

**The ask:** sound visualisers over the page itself, filling the dead black
space, with layers reacting to different parts of the sound.

**What shipped:** the visualiser is still the ring around the album cover. The
`Stage` preset adds a diffuse coloured wash in one corner of the viewport. On a
real look at the live station, the honest verdict is that it does not read as
"the visualiser is on the page" — it reads as a slightly stronger backdrop.

**Why, precisely — this is the useful part.** The stage canvas is full-viewport
and it does paint. But look at what was actually implemented on it:
`_paintStageWash`, `_seedStageBlooms`, `_stageKeepClear`. That is a *bloom wash
only*. The methods that make the visualiser look like a visualiser —
`_paintRing` (the mirrored squircle sweep), `_paintLowLayer`, `_paintShocks`,
`_paintSparks`, `_paintRibbon` — are never called against the stage canvas. They
are still called only against the small `.art-frame` canvas, sized off
`min(w,h) * ART_FRACTION`.

So the shipped stage was never going to satisfy the ask. It is a background
glow that happens to be audio-reactive, not the visualiser at page scale. Two
rounds of tuning `stageOpacity` and `stageScale` could not fix that, because the
geometry isn't there to reveal — which is exactly what the tuning session found
and why it kept looking like "nothing changed".

**How to actually fix it (for a future run, do not start now):**

Run the real paint pipeline against the stage canvas instead of a wash. The
geometry already generalises — `_paint()` takes `(w, h, dt)` and derives
`cx, cy, artHalf, gap, room` from them, so handing it the stage's own dimensions
produces a correctly-proportioned figure at viewport scale with no new maths.
The two things that genuinely need deciding:

- **What plays the role of the album cover.** On the art frame, `artHalf` is the
  hole in the middle of the figure. At page scale that hole should be the on-air
  card's bounding box (read it with `getBoundingClientRect()`), so the sweep
  frames the *card* the way it currently frames the *cover*. Passing a naive
  `min(w,h) * ART_FRACTION` will centre a giant ring behind the text.
- **Cost.** Full pipeline at full viewport is the expensive version of this. The
  existing `TIERS` frame-cost measurement must govern the stage independently,
  and the stage must be the thing that drops out first — the art-frame ring is
  the part Ortis already likes and is never sacrificed for the new one.

`_stageKeepClear` should then be reconsidered rather than kept: it was written to
protect text from a wash at 0.35 opacity, and at 0.90 it is doing most of the
suppression. A real figure needs a real hole, not a blanket mask.

- **The station clock holds.** Two service restarts during deploys, same
  `nowPlayingId` on the other side both times, listeners reconnected without
  doing anything. That is the whole premise of the project and it is solid.

Things worth a roadmap line:

  Passengers - ARTE …`, `?????? ???? ?????? ????????`. The mojibake is a real
  encoding issue in the tag read, not just ugly source data, and it appears in
  the library list, up-next and just-played.

## 5. Where the process needed the most input from Ortis — and how to fix it

Ranked by how much friction each one caused:

1. **Deploys.** By far the worst. Every deploy needed him to open an SSH session,
   paste a privileged block, and paste the output back. One attempt landed in
   PowerShell instead of the Pi; another half-failed because prose inside the
   pasteable block got pasted into the shell, and the failure was only caught by
   checking the Pi independently. **Fix:** a single `npm run ship` that stages
   over SSH, runs the self-test on the Pi, installs and verifies — with a
   `NOPASSWD` sudoers entry scoped to *only* `pi/install.sh`. That converts three
   fragile pastes into one command. Wrap it as a `/tower-ship` slash command so
   the whole thing is one line in a Claude Code tab.
2. **"Where do I run this?"** Real confusion, more than once, and reasonable —
   there are three shells in play (Windows PowerShell, the Pi over SSH, and a
   Claude Code tab) and the prompts didn't say which. **Fix:** every generated
   prompt and every handoff block states its shell on the first line. No
   exceptions.
3. **Verifying a deploy worked.** He had no way to tell, and neither did the
   agent without a browser. The cache bug made this actively misleading twice.
   **Fix:** Job 1 of the pending prompt, plus a `npm run healthcheck` that
   reports the *served* `viz.js` byte length so a stale cache is visible.
4. **Taste calls.** These are the ones that *should* need him — how strong the
   stage is, whether `cover.png` is usable, which look is default. The dev panel
   already made this cheap. Keep pushing decisions into knobs he can drag rather
   than questions he has to answer in prose.
